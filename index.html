⚡ A Quick Word About Hot Reload

Hot reload is the feature most people fall in love with. Normally, checking a small change means stopping your app, waiting for it to rebuild, and starting it again. With omarchy-ios-kit, you save the file and the change appears almost instantly. It turns a slow, stop-start process into something much closer to editing a document.

The practical effect is that you try more ideas. A colour tweak, a different label, a rearranged button — each one takes a second instead of a minute. You learn faster because feedback arrives while the thought is still fresh.

🛟 If Something Goes Wrong

The download will not start

Open the releases link again in a different browser. Some browsers block downloads from unfamiliar pages by default; a second browser usually resolves it.

Windows says the file is unsafe

This appears for software that has not yet built up a reputation with Windows. Choose the option to keep the file, then run it again. Do not disable any safety features on your whole system.

Nothing happens when I double-click

Check that you extracted the download fully rather than opening it from inside the compressed view. Programs behave oddly when run from there. Right-click, choose Extract All, and try again from the extracted folder.

The window opens and then closes straight away

Restart your computer and try once more. This is often caused by an update that is still finishing in the background.

A build fails with a message about a missing piece

Run the setup step from the menu again. It re-checks the supporting files and fetches anything that did not arrive the first time.

My changes do not appear

Confirm hot reload is switched on and that you saved the file. Many editors keep changes in memory until you press save, and the app cannot see what has not been written to disk yet.

📋 Tips From People Who Have Done This Before

  • Keep one folder per app. Mixing projects in a single folder creates confusing errors that are hard to trace.
  • Build before you debug. If a build fails, fix that first. Debugging a broken build wastes time.
  • Read the log from the bottom up. The last line is usually the actual problem; the lines above it are context.
  • Update the kit occasionally. Return to the releases page now and then and check whether a newer version is available. Improvements arrive regularly.
  • Try things on the sample project first. It is safe to break, and you can always replace it.
